4. Major Issues

M1 – Transactional Outbox logical schema conflicts with the C8 canonical envelope

Affected sections:
- Part 7.3 – Transactional Outbox Record
- Part 7.3 §17 – Reliable Asynchronous Message Delivery Architecture

Problem:
The logical Outbox Record requires outbox_event_id, event_type and event_schema_version. C8 requires message_id, contract_id, contract_name, message_kind, schema_version, producer_context, target_context, classification and payload as the canonical external envelope.

The Outbox prose says the envelope or a reproducible protected reference must be retained, but the authoritative logical-field catalogue does not require the C8 contract fields or a canonical envelope reference.

Impact:
Two compliant implementations could persist incompatible Outbox records. Commands may be incorrectly represented as Domain Events, retry identity could diverge between outbox_event_id and message_id, and contract/version governance could be lost.

Required correction:
Replace the old Outbox logical fields with the C8 canonical message fields or explicitly map outbox_event_id to message_id and require a canonical_envelope_reference plus contract, kind, producer/target, classification and schema fields. Rename the purpose from “committed Domain Events” to approved Integration Events and Integration Commands.

M2 – C10 logical records are not integrated into the authoritative C4 persistence catalogues

Affected sections:
- C10 Privacy Logical Records
- Part 7.2 aggregate/entity inventory
- Part 7.3 complete persistence inventory
- Part 7.3 relationship/constraint catalogue
- Part 7.3 retention matrix
- Part 7.3 transaction-boundary catalogue
- Part 7.3 index/access-pattern catalogue

Problem:
Terms Acceptance Receipt, Privacy Notice Receipt, Consent Record, Privacy Request, Identifier Tombstone and Privacy Execution Record are described in one consolidated prose block. They are not consistently added to the authoritative inventory, aggregate ownership, relationship, retention, transaction and index catalogues that C4 declares complete.

Impact:
Implementers cannot determine authoritative aggregate ownership, foreign-key behavior, retention class, transaction scope or required query/index patterns without inventing decisions.

Required correction:
Add each C10 record to every applicable C4 catalogue, including ownership classification, relationships, constraints, retention, deletion behavior, transaction boundary and approved access patterns.

M3 – C10 asynchronous contracts are outside the authoritative C8 contract catalogue

Affected sections:
- Part 7.2 §10 – Approved Cross-Module Command Catalogue
- Part 7.2 §10 – Approved Integration Event Catalogue
- C10 Privacy Coordination Contracts

Problem:
M01-CMD-004, PRV-CMD-001 and M01-EVT-003 appear under a later implementation-gate area rather than the authoritative C8 contract catalogue. They lack the same structured producer, authoritative consumer, aggregate, payload, ownership and outcome definitions used by C8.

Impact:
The document simultaneously states that uncatalogued external messages cannot be published and introduces three privacy messages outside that catalogue.

Required correction:
Move the three contracts into a clearly labelled “Proposed/Gated C10 Contracts” subsection within Part 7.2 §10. Define their envelope, producer, consumer, payload, completion semantics, privacy classification and gating. Keep them non-implementable until the orchestrator is approved.

M4 – Deletion state and Privacy Request state have no authoritative mapping

Affected sections:
- Part 1 §38 – Canonical Deletion States
- Part 6 – Canonical Privacy Request States
- Part 7.3 – Privacy Request
- M01-ID-002, M01-ID-003 and M01-ID-005

Problem:
The document defines one Deletion state machine and a second Privacy Request state machine. The Privacy Request logical record says it uses a canonical state without naming which state set applies. M01-ID-005 returns deletionState, but it is not explicit whether that is the Deletion state, Privacy Request state or a safe projection.

Impact:
Persistence, API responses, optimistic concurrency and cross-module orchestration may implement different state machines for the same request.

Required correction:
Define Privacy Request as the orchestration state and Deletion Execution as a DELETION-specific child state, or define one canonical mapping table. State explicitly which value M01-ID-002/003/005 reads and returns, and define the safe external projection.

M5 – Consolidated document numbering and repeated final sections are ambiguous

Affected headings include:
- “26. Cross-Module Outputs” – repeated four times
- “28. Final Architecture Review” – repeated four times
- “29. Architecture Decision References” – repeated four times
- “29. Final Architecture Review” – repeated twice
- repeated “1. Objective” and “2. Scope” headings across embedded documents

Problem:
The merged document retains independently numbered subdocuments without a unique hierarchical identifier in every heading.

Impact:
References such as “Part 10.5 §29” are not reliably resolvable by heading text alone. Review findings, requirements traceability and future change requests can target the wrong section.

Required correction:
Assign stable hierarchical identifiers, for example 10.1.26, 10.2.26 and 10.6.29, or prefix every repeated heading with its Part/subpart document identifier. Preserve business terminology while removing numbering ambiguity.

M6 – Final document-control statement is stale and contradicts v1.11

Affected section:
- Part 10.6 §30 – Module 01 Draft Status

Problem:
The final statement says “Module 01 Corrected Draft v1.1 remains Draft” and describes only Critical Correction 1. The actual consolidated document is v1.11 and contains C1–C10.

Impact:
The authoritative version and correction scope are misrepresented in the final document-control section.

Required correction:
Replace the stale statement with v1.11, list C1–C10 as incorporated corrections, preserve Draft status and state that final approval remains pending.

5. Minor Issues

m1 – Legacy identity-type terminology

“Admin Identity provisioning,” “Super Admin Identity bootstrap” and related headings remain. Their surrounding rules correctly describe one universal Identity subject to authentication-security classification, but the wording conflicts with the C1 terminology standard.

Recommendation:
Use “Privileged Admin access Identity provisioning” and “Super Admin access bootstrap” without creating new Identity types.

m2 – Encoding corruption

Six mojibake occurrences remain, including Module 02/03/06 ownership separators and Proposed ADR-M01-014/015/016 headings.

Recommendation:
Normalize the file as UTF-8 and replace corrupted separators with the intended en dash or plain hyphen.

m3 – Embedded version headers are not indexed

The consolidated document contains the overall Version 1.11 plus numerous embedded Version 1.0 headers and one Version 1.1 header. Embedded component versions may be legitimate, but no component-version index explains them.

Recommendation:
Add a document-control table mapping each Part/subpart to its component version and consolidated version.

m4 – Noncanonical compressed ADR reference

The C10 ADR section says “ADR-M01-001/002/003,” which is not a valid individual ADR identifier format.

Recommendation:
Write ADR-M01-001, ADR-M01-002 and ADR-M01-003 separately.

m5 – C10 status DTO needs an explicit state projection name

M01-ID-005 returns “deletionState,” but a stable enum/schema name and mapping are not stated.

Recommendation:
Define a safe DeletionStatus DTO enum after resolving M4.
