2. Approved C2 Model Applied

- JWT signature and claim validation prove token integrity and issuance, but do not independently prove that the referenced Session remains valid.
- Every protected request requires current Session-state and Session-Version validation.
- PostgreSQL is authoritative for Session and Refresh Token state.
- Redis contains only a non-authoritative Session Validation Projection.
- Canonical Session states are ACTIVE, REVOKED and EXPIRED.
- Refresh Tokens are opaque protected credentials with ACTIVE, USED, REVOKED and EXPIRED states.
- Refresh Token rotation is atomic and creates exactly one successor.
- Confirmed Refresh Token reuse revokes the token family and associated Session and increments Session Version.
- Logout, logout-all and security invalidation commit authoritative revocation before reporting success.
- Revocation is idempotent. Requests beginning validation after committed revocation are rejected; the explicitly defined in-flight boundary applies to requests validated before the commit.

4. Deletions and Replacements

Replaced or removed as governing rules:
- The statement that JWTs provide stateless authentication without mandatory current Session validation.
- Ambiguous Access Token invalidation that depended only on token expiry.
- Non-canonical Session lifecycle stages used as persisted Session states.
- Refresh Token rotation semantics that did not guarantee one atomic successor.
- Revocation behavior without a committed authoritative-state boundary.
- Logout behavior that could wait for Access Token expiration.

5. Additions

Added:
- sessionVersion Access Token claim and comparison rule.
- Mandatory protected-request Session validation order.
- PostgreSQL authoritative Session and Refresh Token state.
- Redis Session Validation Projection with fail-closed miss, stale and inconsistency behavior.
- ACTIVE, REVOKED and EXPIRED canonical Session states.
- ACTIVE, USED, REVOKED and EXPIRED Refresh Token states.
- Atomic single-use Refresh Token rotation.
- Token-family and Session revocation after confirmed reuse.
- Idempotent logout, logout-all and revocation behavior.
- Committed-revocation and in-flight-request semantics.
- Domain relationships, audit events, monitoring categories and C2-specific tests.

7. C2 Verification Checklist

JWT and Protected Requests
- Pass – JWT cryptographic validation is explicitly distinguished from authenticated-request acceptance.
- Pass – A valid JWT signature alone does not prove current Session validity.
- Pass – Every protected request validates the referenced Session.
- Pass – Every protected request validates the token sessionVersion against authoritative current Session Version.
- Pass – Invalid, missing, expired, revoked or version-mismatched Sessions are rejected.

Authoritative State and Cache
- Pass – PostgreSQL is authoritative for Session state.
- Pass – PostgreSQL is authoritative for Refresh Token state.
- Pass – Redis is explicitly non-authoritative.
- Pass – Redis contains a bounded Session Validation Projection.
- Pass – Cache miss requires authoritative lookup before access is accepted.
- Pass – Stale, inconsistent or unverifiable cache state cannot grant access.

Session Lifecycle
- Pass – Canonical Session states are ACTIVE, REVOKED and EXPIRED.
- Pass – Activity, refresh and logout are not incorrectly modeled as canonical Session states.
- Pass – Idle and absolute expiration are represented and enforced.
- Pass – Session Version changes invalidate stale Access Tokens.

Refresh Tokens
- Pass – Refresh Tokens are opaque protected credentials.
- Pass – Refresh Token states are ACTIVE, USED, REVOKED and EXPIRED.
- Pass – Rotation consumes the presented token atomically.
- Pass – Exactly one successor is created by a successful rotation.
- Pass – Concurrent refresh attempts cannot create two valid successors.
- Pass – Confirmed reuse revokes the token family and associated Session.
- Pass – Confirmed reuse increments Session Version.

Revocation and Logout
- Pass – Logout commits authoritative Session revocation before success.
- Pass – Logout All Devices revokes all applicable Sessions, including the initiating Session.
- Pass – Revocation is idempotent.
- Pass – Requests beginning validation after committed revocation are rejected.
- Pass – The in-flight boundary is explicitly defined.
- Pass – Revocation does not depend on waiting for Access Token expiry.

Architecture and Documentation
- Pass – Parts 1, 3, 5, 6, 7, 8 and 10 use consistent C2 terminology.
- Pass – Domain relationships and events support the C2 lifecycle.
- Pass – Monitoring distinguishes token, Session, cache and propagation failures.
- Pass – Testing covers state, version, rotation, reuse, concurrency, logout and fail-closed recovery.
- Pass – Proposed ADR-M01-004 remains Proposed.
- Pass – The document remains Draft.
- Pass – Module 01 Corrected Draft v1.2.txt remains preserved.
- Pass – No C3 or later correction was applied.
