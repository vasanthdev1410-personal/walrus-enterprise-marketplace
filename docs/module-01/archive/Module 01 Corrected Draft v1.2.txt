4. Authentication Principles

The authentication system shall follow these principles:

Secure by default

Every protected resource shall deny access unless authentication requirements are satisfied.

Least privilege

Authentication proves identity only. Authorization permissions shall be handled separately through approved role and permission rules.

Server-side enforcement

All authentication, verification, session, and account-state checks shall be enforced by the backend.

Client-side validation shall never be treated as a security control.

Minimal disclosure

Authentication APIs shall return only the information required by the requesting client.

Passwords, password hashes, OTP values, token hashes, secrets, and internal security metadata shall never be returned.

Explicit lifecycle

Every identity shall move through clearly defined states.

Auditable activity

Security-sensitive authentication actions shall create structured audit records.

Revocability

Sessions and refresh tokens must be revocable without deleting the user account.

Fail securely

Unexpected authentication failures shall deny access and return standardized safe error responses.

These principles align with current digital-identity lifecycle guidance and modern authentication security practice.

6. Customer Profile Boundary

A Customer profile represents marketplace customer information and customer business capabilities associated with an Identity.

Module 06 – Customer Management shall own the Customer profile.

Module 01 may create and authenticate the underlying Identity but shall not own customer-profile data or determine customer permissions.

Customer self-registration shall:

Create or locate the Module 01 Identity
Complete the required identity verification
Request creation or association of a Customer profile through an approved Module 06 contract
Request any required customer role assignment through an approved Module 02 contract

Creating a Customer profile or assigning a Customer role shall not create a second Identity.

Customer permissions shall be determined exclusively by Module 02.

7. Seller Profile Boundary

A Seller profile represents seller-specific business information associated with an Identity.

Module 03 – Seller Management shall own:

Seller profiles
Seller organizations
Seller business onboarding
Seller approval
GST verification
PAN verification
Bank verification
Warehouse setup
Commission agreements
Seller business status

Module 01 may create and authenticate the underlying Identity but shall not own seller-profile or seller-onboarding data.

Seller self-registration shall:

Create or locate the Module 01 Identity
Complete the required identity verification
Request creation or association of a Seller profile through an approved Module 03 contract
Request any required seller role assignment through an approved Module 02 contract

Creating a Seller profile or assigning a Seller role shall not create a second Identity.

Seller permissions shall be determined exclusively by Module 02.

8. Admin Authentication-Security Classification

Admin is a Module 02 authorization role and is not part of the Module 01 Identity model.

Module 02 shall own the Admin role and all permissions associated with that role.

Module 01 shall own an authentication-security classification that identifies an Identity as subject to privileged-administrator authentication controls.

Approved classification:

PRIVILEGED_ADMIN_AUTHENTICATION

This classification shall control authentication security only, including:

Mandatory MFA
Approved authentication methods
Web-only authentication in Phase 1
Privileged-session timeout requirements
Enhanced authentication audit requirements
Privileged-account recovery requirements

The classification shall not grant Admin permissions and shall not constitute an Admin role assignment.

An Identity shall receive Admin access only when:

Module 01 has successfully applied the required privileged authentication-security classification;
Module 01 authentication requirements have been satisfied; and
Module 02 has assigned the Admin role through its approved authorization workflow.

9. Super Admin Authentication-Security Classification

Super Admin is a Module 02 authorization role and is not part of the Module 01 Identity model.

Module 02 shall own the Super Admin role and all permissions associated with that role.

Module 01 shall own an authentication-security classification that identifies an Identity as subject to the highest approved privileged-authentication controls.

Approved classification:

SUPER_ADMIN_AUTHENTICATION

This classification shall control authentication security only, including:

Mandatory MFA
Approved high-assurance authentication methods
Web-only authentication in Phase 1
Restricted provisioning
Privileged-session timeout requirements
Enhanced authentication audit requirements
Privileged-account recovery requirements
Bootstrap authentication controls

The classification shall not grant Super Admin permissions and shall not constitute a Super Admin role assignment.

An Identity shall receive Super Admin access only when:

Module 01 has successfully applied the required Super Admin authentication-security classification;
Module 01 authentication requirements have been satisfied; and
Module 02 has assigned the Super Admin role through its approved authorization workflow.

The initial controlled bootstrap process shall provision Module 01 authentication state and Module 02 authorization state through their respective approved ownership boundaries.

Direct cross-module database modification is prohibited.

SUSPENDED	Administratively restricted
DISABLED	Access intentionally disabled
DELETED	Account removed or anonymized according to approved policy

State transitions shall be validated by the backend.

Approved basic transitions

23. Authentication Assurance Model
Objective

Authentication Assurance represents the strength of the authentication completed for the current session.

Authentication Assurance shall be owned and calculated by Module 01.

Authentication Assurance shall not represent:

Customer or Seller profile status
Admin or Super Admin role assignment
Business approval
Identity type
Authorization permission
MFA enrollment without successful MFA verification

Approved Assurance Levels

Assurance Level	Meaning
AAL0	No authenticated session exists
AAL1	The current session completed one approved primary authentication factor
AAL2	The current session completed an approved primary factor and an approved independent MFA factor

AAL0 shall not be issued as an authenticated session assurance value.

Email or mobile ownership verification shall remain verification state and shall not independently raise the assurance level of a session.

MFA enrollment alone shall not produce AAL2.

AAL2 shall be established only when an approved MFA factor is successfully verified for the current authentication event or approved step-up authentication event.

Admin and Super Admin roles shall not produce an assurance level.

Module 01 authentication-security classifications may require a minimum assurance level but shall not grant authorization.
24. Authentication Boundaries

Authentication and authorization shall remain independent architectural concerns.

Authentication

Authentication establishes:

Who the user is.

Authentication confirms identity using approved credentials.

Authentication does not determine system permissions.

Authorization

Authorization determines:

What an authenticated user is permitted to access.

Authorization shall be implemented through the approved Role-Based Access Control (RBAC) model defined in Module 02.

Authentication shall never directly grant application permissions.

33. Authentication Assurance Calculation
Objective

Module 01 shall calculate Authentication Assurance from authentication factors successfully completed for the current session.

Approved Calculation

Condition	Authentication Assurance
No authenticated session	AAL0
Approved primary authentication completed	AAL1
Approved primary authentication and approved MFA factor completed	AAL2

Calculation Rules

Authentication Assurance shall:

Be calculated by Module 01
Be bound to the current session and authentication event
Record the authentication methods used
Record the authentication timestamp
Be recalculated after approved step-up authentication
Expire according to the applicable authentication policy
Never be assigned by a client
Never be derived from a Module 02 role
Never be derived solely from MFA enrollment
Never be derived from Customer or Seller profile state

PRIVILEGED_ADMIN_AUTHENTICATION shall require AAL2 before a privileged session is established.

SUPER_ADMIN_AUTHENTICATION shall require AAL2 before a privileged session is established.

Authorization requirements based on assurance shall be evaluated by Module 02 using the approved authenticated identity context.

3. Authentication Principles

The authentication platform shall follow the principles below.

3.1 Identity Before Access

Authentication shall always establish identity before access to protected resources.

Authentication shall never directly grant permissions.

3.2 Separation of Responsibilities

Authentication determines:

Who the user is.

Authorization determines:

What the authenticated identity may access.

Permission evaluation shall occur after successful authentication.

3.3 Backend Authority

Authentication decisions shall always be made by the backend.

Client applications shall never determine authentication status.

3.4 Zero Trust

Every protected request shall require authentication validation.

Authenticated requests shall never be trusted solely because previous requests were authenticated.

3.5 Secure by Default

Authentication services shall deny access whenever validation cannot be completed successfully.

Unexpected failures shall result in access denial rather than access approval.

3.6 Auditability

Authentication events shall generate immutable audit records.

Authentication failures shall be auditable.

Authentication successes shall be auditable.

Security-sensitive operations shall be fully traceable.

3.7 Revocability

Authentication shall support immediate session revocation.

Credential revocation shall not require identity deletion.

3.8 Multi-Device Support

A single authenticated identity may maintain multiple concurrent authenticated sessions.

Each session shall remain independently managed.

JWT performance

3. Verification Principles

The verification platform shall follow the principles below.

3.1 Backend Authority

Verification decisions shall be made exclusively by the backend.

Client applications shall not:

Mark an email as verified
Mark a mobile number as verified
Approve an OTP
Activate MFA
Generate recovery codes
Modify verification state directly

Client-side validation shall improve usability only.

3.2 Purpose-Bound Verification

Every verification request shall have one approved purpose.

Examples include:

Registration email verification
Registration mobile verification
Password-reset verification
Contact-change verification
Admin invitation verification
MFA verification
Sensitive-operation confirmation

An OTP or verification challenge created for one purpose shall not be accepted for another purpose.

3.3 Identity Binding

Every verification challenge shall be bound to:

One identity or pending registration
One destination
One verification purpose
One verification channel
One expiration time

Verification challenges shall not be transferable between identities.

3.4 Short-Lived Verification

OTPs and verification challenges shall remain valid only for a limited, centrally configurable duration.

Expired challenges shall never be reactivated.

A new challenge shall be generated when verification is attempted after expiration.

3.5 Single Use

Every successfully used OTP, recovery code, or verification challenge shall become invalid immediately.

Successful verification shall prevent replay of the same challenge.

3.6 Minimal Disclosure

Verification responses shall not expose whether an unrelated identity exists.

Public responses shall not reveal:

Registered email addresses
Registered mobile numbers
OTP values
MFA secrets
Recovery codes
Internal verification counters
Internal risk scores
Provider credentials
Administrative account details
3.7 Rate Limiting

Verification requests, OTP generation, OTP validation, and resend operations shall be rate limited.

Limits shall be enforceable using combinations of:

Identity identifier
Pending-registration identifier
Email address
Mobile number
IP address
Device identifier
Verification purpose

Rate-limit values shall remain centrally configurable.

3.8 Auditability

Security-sensitive verification actions shall generate audit records.

Audit events shall include:

Verification requested
Delivery initiated
Delivery failed
Verification succeeded
Verification failed
OTP expired
OTP resend requested
Attempt limit exceeded
MFA enrolled
MFA challenged
MFA succeeded
MFA failed
Recovery code used
Trusted device added
Trusted device revoked

OTP values, MFA secrets, and raw recovery codes shall never appear in audit logs.

3.9 Secure Failure

When verification cannot be completed safely, the system shall deny the operation.

Provider failures, Redis failures, unexpected exceptions, or validation uncertainty shall not result in automatic verification.

3.10 Channel Independence

Email verification and mobile verification shall be tracked independently.

Verification of one channel shall not automatically verify another channel.

Examples:

Verified email does not imply verified mobile.
Verified mobile does not imply verified email.
MFA enrollment does not imply verification of an unrelated contact method.

Part 6 – Authentication-to-Authorization Integration Boundary

Document ID: WEMP-M01-006

Version: 1.1

Status: Draft

Classification: Confidential – Internal Use Only

1. Objective

Part 6 defines the integration boundary between Module 01 – Identity & Authentication and Module 02 – Role & Permission Management.

Module 01 authenticates an identity and produces a trusted authenticated identity context. Module 02 consumes that context and independently determines whether the identity is authorized to perform a requested action.

Authentication and authorization shall remain separate architectural responsibilities.

2. Module 01 Ownership

Module 01 owns only:

Identity records and identity lifecycle
Authentication credentials
Registration and verification
OTP and MFA
Authentication sessions and devices
Access-token and refresh-token lifecycle
Identity recovery
Authenticated identity context creation
Authentication security events and authentication audit records

Module 01 shall not own or define roles, permissions, role assignments, permission assignments, role hierarchy, resource authorization policies, temporary permissions, delegated administration, or authorization decisions.

3. Module 02 Ownership

Module 02 owns:

Roles and permissions
Role and permission assignments
Role hierarchy
Resource authorization policies
Temporary permissions
Delegated authorization administration
Authorization evaluation and decisions
Authorization audit events

The detailed authorization model, persistence model, APIs, events, caching strategy, testing strategy, monitoring rules, and governance shall be defined and approved in Module 02.
Module 02 role assignment and role revocation shall remain Module 02 operations.

When a privileged role assignment or revocation requires an authentication-security classification or session change, Module 02 shall send an approved versioned and idempotent request or event to Module 01.

Module 02 shall not modify Module 01 Identity or session records directly.

Partial or failed cross-module processing shall not grant privileged access.

4. Authenticated Identity Context

After successful authentication, Module 01 shall provide a trusted authenticated identity context containing only:

Identity Identifier
Session Identifier
Authentication Timestamp
Authentication Method
Authentication Assurance Level
Current MFA State
Device-Session Identifier
Correlation Identifier

The authenticated identity context shall not contain business roles, business permissions, permission matrices, resource policies, or precomputed authorization decisions.

5. Request Processing Boundary

The required processing sequence is:

Client Request
        ↓
Module 01 Authentication Validation
        ↓
Authenticated Identity Context
        ↓
Module 02 Authorization Evaluation
        ↓
Business Module Execution only when Module 02 grants access

Module 01 authentication middleware and guards shall authenticate requests only. They shall not grant business access or evaluate business permissions.

Module 02 shall consume the authenticated identity context through approved service contracts. Direct database coupling between Module 01 and Module 02 is prohibited.

6. Failure Boundary

If Module 01 cannot authenticate the request safely, the request shall be rejected before authorization evaluation.

If Module 02 cannot evaluate authorization safely, Module 02 shall deny access according to its approved secure-failure policy.

An authentication success shall never imply authorization success.

7. Audit and Observability Boundary

Module 01 owns authentication, session, verification, MFA, device, and recovery audit events and telemetry.

Module 02 owns authorization-policy, role, permission, assignment, and authorization-decision audit events and telemetry.

Correlation identifiers shall enable cross-module tracing without transferring data ownership.

8. Testing Boundary

Module 01 shall test authentication enforcement and the correctness, integrity, and secure handoff of the authenticated identity context.

Module 02 shall test roles, permissions, assignments, authorization policies, authorization decisions, deny-by-default behavior, and privilege-escalation controls.

Cross-module integration tests shall verify that Module 02 consumes the Module 01 context through approved contracts and that no direct database coupling exists.

9. Cross-Module Outputs

Part 6 produces:

Authentication-to-Authorization Integration Boundary
Authenticated Identity Context Contract
Authentication Handoff Requirements
Audit and Observability Ownership Boundary
Testing Ownership Boundary
Proposed Authentication-to-Authorization Boundary ADR

10. Acceptance Criteria

Part 6 is complete for draft review when:

Module ownership is explicit.
The authenticated identity context contains no business authorization data.
Authentication middleware performs no business authorization evaluation.
Direct database coupling is prohibited.
Audit, monitoring, and testing ownership are separated.
Module 02 remains the authoritative owner of authorization.
No implementation-specific source code has been introduced.

11. Proposed Architecture Decision Record

ADR: Proposed ADR-M01-004 – Authentication-to-Authorization Boundary

Status: Proposed

Context

Module 01 must provide trustworthy authentication results to Module 02 without owning or duplicating authorization capabilities.

Decision

Module 01 shall own the universal Identity, identity authentication lifecycle, authentication-security classifications and session Authentication Assurance.

Module 03 shall own Seller profiles, seller organizations, seller onboarding and seller business status.

Module 06 shall own Customer profiles and customer business data.

Module 02 shall own roles, permissions, assignments, authorization policies, authorization evaluation and authorization decisions.

JWTs, sessions and the authenticated identity context shall contain authentication information only and shall not contain roles, permissions, profile state, user-type claims or authorization decisions.

Integration shall use approved versioned contracts, stable Identity Identifiers and correlation identifiers. Direct database coupling and cross-module foreign keys are prohibited.

Consequences

Authentication and authorization can evolve independently.
Shared business authorization data is not embedded in Module 01 tokens or persistence.
Module 02 can be separated into an independent service later without redesigning Module 01 domain ownership.
Cross-module contract, audit-correlation, failure, and integration testing requirements become mandatory.

This ADR remains Proposed and does not supersede any approved ADR until formally reviewed and approved.

3.3 Repeatability

Equivalent test executions shall consistently produce equivalent results under identical conditions.

Tests shall remain deterministic.

3.4 Independent Verification

Testing shall verify system behavior independently of implementation details.

Tests shall validate externally observable outcomes.

3.5 Shift-Left Quality

Quality assurance activities shall occur as early as possible within the development lifecycle.

Architecture, APIs, validation, and security shall be verified before production deployment.

3.6 Risk-Based Testing

Testing effort shall prioritize:

Authentication
Authorization
Identity security
Financial workflows
Administrative operations
Critical business functionality

Lower-risk functionality may receive proportionally reduced testing.

3.7 Traceability

Every requirement shall be traceable to one or more approved test cases.

Every critical defect shall be traceable to the affected requirement.

3.8 Continuous Quality

Testing shall support continuous validation throughout development.

Quality shall remain measurable throughout the software lifecycle.
